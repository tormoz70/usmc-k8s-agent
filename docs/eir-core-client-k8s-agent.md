# ЭИР: core-client(Java) -- k8s-agent(Golang)

> ЭИР -- инженерная запись решения. Документ фиксирует выбранные архитектурные решения для связки `core-client(Java)` -- `k8s-agent(Golang)`.

## 1. Статус

Черновик для обсуждения.

## 2. Контекст

Нужно разработать сервис `k8s-agent`, который устанавливается в Kubernetes-кластер и выполняет команды через Kubernetes API / Istio API. Команды приходят из Kafka. Источником команд выступает `core-client(Java)`.

Требования:

- агент написан на Golang;
- core-client написан на Java;
- транспорт команд -- Kafka;
- агент работает in-cluster;
- агент обращается к kube-apiserver и Istio API;
- агент использует informers/watchers;
- нужны надёжность, идемпотентность, обратная связь и безопасная модель прав.

## 3. Принятые решения

### 3.1. Использовать асинхронную Kafka-интеграцию между core-client и агентом

`core-client(Java)` публикует команды в топик `k8s.commands`. `k8s-agent(Golang)` читает этот топик как consumer group и публикует результаты в `k8s.command-results`.

Последствия:

- core-client не зависит от прямой доступности kube-apiserver;
- команды можно буферизовать;
- возможна at-least-once доставка, значит обязательна идемпотентность;
- результат выполнения становится асинхронным.

### 3.2. Не давать core-client прямой доступ к Kubernetes API

Kubernetes credentials и RBAC получает только `k8s-agent`.

Последствия:

- уменьшается blast radius core-client;
- Kubernetes RBAC сосредоточен в одном месте;
- все действия проходят через единый аудит агента;
- агент становится обязательной точкой контроля и валидации.

### 3.3. Использовать гибридную модель агента

Базовая модель -- командный процессор поверх Kafka. Generic Kubernetes/Istio операции идут через HTTP-over-Kafka, а высокоуровневые задания вроде `logs.collect` идут как отдельные typed commands.

Последствия:

- агент исполняет команды и публикует результаты, без фоновых коррекций ресурсов;
- каждая команда исполняется как отдельный request/reply сценарий;
- нужно аккуратно проектировать интерфейсы handler-слоя.

### 3.4. Использовать `segmentio/kafka-go` как Kafka-клиент в k8s-agent

Причины:

- чистый Go, без cgo;
- проще сборка контейнерного образа;
- достаточно возможностей для consumer group, producer, commit offset, retries.

Альтернативы:

- `confluent-kafka-go` -- больше возможностей, но требует librdkafka/cgo;
- `IBM/sarama` -- зрелый клиент, но более сложный API.

Последствия:

- проще CI/CD и container image;
- меньше платформенных зависимостей;
- при необходимости advanced Kafka-фич решение можно пересмотреть.

### 3.5. Использовать `client-go` dynamic client + RESTMapper

Агент работает с Kubernetes и Istio ресурсами через dynamic client и discovery/RESTMapper.

Причины:

- один механизм для Kubernetes built-in ресурсов и Istio CRD;
- не нужно генерировать типизированные клиенты для каждой CRD;
- проще поддерживать новые resource kinds.

Альтернативы:

- типизированные Kubernetes/Istio clients;
- прямой REST client поверх `client-go`.

Последствия:

- payload валидируется в рантайме, а не компилятором;
- нужна строгая runtime-валидация команд и allow-list;
- для сложных Istio-сценариев можно добавить типизированные клиенты точечно.

### 3.6. Использовать JSON envelope в первой версии контракта

Команда и результат описываются JSON-сообщениями.

Причины:

- проще стартовая интеграция Java и Go;
- удобно отлаживать сообщения;
- не требуется Schema Registry на первом этапе.

Последствия:

- нужна явная версия схемы в будущем;
- нужна строгая валидация envelope;
- при росте количества клиентов стоит рассмотреть Protobuf/Avro + Schema Registry.

### 3.7. Использовать Kafka key для упорядочивания команд по ресурсу

Kafka key формируется как:

```text
<cluster>/<namespace>/<group>/<kind>/<name>
```

Последствия:

- команды по одному ресурсу попадают в одну партицию;
- порядок гарантирован внутри партиции;
- общий параллелизм ограничен числом партиций;
- core-client должен стабильно формировать ключ.

### 3.8. Использовать server-side apply для идемпотентных изменений

Для `apply`-операций агент использует Kubernetes server-side apply с фиксированным `fieldManager`.

Последствия:

- повтор команды с тем же payload не должен ломать состояние;
- конфликт владения полями можно явно обрабатывать;
- нужны правила для force apply.

### 3.9. Использовать DLQ для терминальных ошибок

Сообщения, которые невозможно обработать корректно, отправляются в `k8s.commands.dlq` вместе с причиной ошибки.

В DLQ отправляются:

- невалидный JSON;
- неизвестная версия envelope;
- неподдерживаемый `type`;
- операция запрещена allow-list;
- payload не проходит валидацию;
- превышен лимит retry для терминальной ошибки.

Последствия:

- основной consumer не блокируется ядовитым сообщением;
- нужен процесс разбора DLQ;
- DLQ payload не должен содержать секреты.

### 3.10. Использовать result topic для обратной связи

Агент публикует результат обработки в `k8s.command-results`.

Последствия:

- core-client может асинхронно показать статус;
- можно строить аудит по `command_id`;
- нужно определить срок хранения результатов в Kafka.

### 3.11. Использовать ServiceAccount + RBAC с минимальными правами

Агент работает под выделенным ServiceAccount. Права задаются Role/ClusterRole в зависимости от того, какие namespaces и ресурсы разрешены.

Последствия:

- безопасность не зависит только от валидации сообщений;
- для cluster-scoped ресурсов нужны отдельные ClusterRole;
- набор RBAC должен соответствовать allow-list команд.

### 3.12. Использовать informers/watchers как кэш и источник событий

Informers/watchers используются для:

- чтения актуального состояния перед выполнением команды;
- снижения нагрузки на kube-apiserver;
- отслеживания изменений управляемых ресурсов и публикации событий в Kafka.

Последствия:

- на старте агента нужно дождаться синхронизации кэша;
- нужно контролировать список watched resources;
- informer cache может быть eventually consistent, для критичных операций допустимо дополнительное live-read обращение к API.

### 3.13. Использовать leader election для эксклюзивных операций

Агент разворачивается как Deployment с несколькими репликами. Для операций, которые не должны выполняться параллельно несколькими pod-ами, используется Kubernetes Lease.

Последствия:

- можно безопасно держать несколько реплик агента;
- consumer-group параллелизм всё равно определяется числом Kafka partitions;
- нужно явно определить, какие части агента активны только у лидера.

## 4. Альтернативы, которые не выбраны сейчас

### 4.1. Синхронный HTTP/gRPC вызов агента из core-client

Не выбран, потому что:

- усложняет сетевой доступ к агенту внутри кластера;
- хуже переносит временную недоступность Kubernetes API;
- не даёт естественного буфера команд.

### 4.2. Прямой доступ core-client к kube-apiserver

Не выбран из-за рисков безопасности и усложнения RBAC/credentials management.

## 5. Риски и меры снижения

| Риск | Мера |
| --- | --- |
| Дубли Kafka-сообщений | `idempotency_key`, server-side apply, стабильный Kafka key |
| Выполнение опасной команды | allow-list, RBAC, dry-run, отдельные политики для delete/scale/Istio security |
| Ядовитое сообщение блокирует consumer | DLQ + terminal error classification |
| Несогласованность informer cache | ожидание cache sync, live-read для критичных операций |
| Чрезмерные права агента | минимальный RBAC, раздельные роли по namespaces/resources |
| Потеря результата | result topic, ретраи producer-а, корреляция по `command_id` |
| Неправильный порядок команд | Kafka key по resource identity |

## 6. Решения, требующие уточнения

1. Набор разрешённых `command.type` для первой версии.
2. Набор Kubernetes и Istio ресурсов для первой версии.
3. Нужна ли криптографическая подпись команды поверх Kafka ACL.
4. Нужен ли отдельный persistent storage истории команд.
5. Политика retry и backoff по типам ошибок.
6. Правила dry-run/approval для опасных операций.
