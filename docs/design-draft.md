# Драфт: сервис-агент для выполнения команд в Kubernetes из Kafka

> Статус: черновик для обсуждения. Стек: **Golang, Kafka, Kubernetes**.
> Кода пока нет — сначала фиксируем варианты архитектуры и закрываем открытые вопросы.

## Как понята задача

Сервис («агент»):

- крутится **внутри** k8s-кластера (in-cluster);
- слушает **топик Kafka**, получает оттуда команды;
- выполняет команды против **kube-apiserver** и **Istio API** (CRD `networking.istio.io`, `security.istio.io` и т.д.);
- использует **informers/watchers** — то есть не только пишет в API, но и наблюдает за состоянием кластера.

Дальше всё зависит от пары ключевых развилок (см. раздел «Вопросы»), но архитектурно вырисовывается несколько вариантов.

## Сквозные технические решения (общие для всех вариантов)

### 1. Доступ к kube/Istio API

- `client-go` — база. Для Istio либо типизированный `istio.io/client-go`, либо `dynamic.Interface` + `unstructured` (работает с любыми CRD без перегенерации клиента).
- Рекомендация: **dynamic client + RESTMapper** как универсальный путь (kube + Istio + любые CRD одним механизмом), а типизированные клиенты подключать точечно, где нужна строгая схема.

### 2. Аутентификация и права

- `ServiceAccount` + **RBAC**, права выдаём по принципу наименьших привилегий (а не cluster-admin).
- Это критично для безопасности: агент исполняет команды «снаружи», поэтому RBAC = последняя линия защиты.

### 3. Kafka-клиент (три кандидата)

- `segmentio/kafka-go` — чистый Go, без cgo, простой. **Дефолт.**
- `confluent-kafka-go` — на базе librdkafka (cgo), максимум фич, но усложняет сборку/образ.
- `IBM/sarama` — популярный, но более «низкоуровневый» и капризный по offset-менеджменту.

### 4. Контракт сообщений

- Конверт команды: `command_id`, `type`, `idempotency_key`, `target` (group/version/kind, namespace, name), `payload`, `dry_run`, `issued_by`, `ts`.
- Формат: JSON для старта; если важна эволюция схемы — Protobuf/Avro + Schema Registry.

### 5. Надёжность обработки

- Идемпотентность (по `idempotency_key` или через server-side apply с `fieldManager`).
- Ретраи + **DLQ** (dead-letter topic) для «ядовитых» сообщений.
- Сериализация по ключу: класть ключом Kafka-сообщения `namespace/name`, чтобы команды по одному ресурсу шли в одну партицию и обрабатывались по порядку.

### 6. Обратная связь

- Топик-результат (`commands.results`) со статусом выполнения + k8s Events + метрики Prometheus.

### 7. Деплой

- `Deployment`, **leader election** (через `coordination.k8s.io/Lease`), чтобы при нескольких репликах команды/реконсайл не выполнялись параллельно несколькими подами.
- Замечание про масштабирование: в consumer-group **одну партицию читает один консьюмер**, поэтому параллелизм потребления = число партиций, а не реплик.

## Вариант A — «Тонкий исполнитель команд» (императивный)

Kafka-консьюмер → валидация → прямой вызов dynamic client (`create/apply/patch/delete`). Informers используются как **кэш для валидации и enrich** (проверить, что ресурс существует, подтянуть текущее состояние).

- ➕ Простой, быстрый к реализации, прозрачный «команда → действие».
- ➕ Минимум инфраструктуры.
- ➖ Нет автоматического «выравнивания» состояния: выполнили команду и забыли. Если кто-то снаружи поменял ресурс — агент не среагирует.
- ➖ Логику идемпотентности/ретраев пишем сами.

**Когда брать:** если задача — «выполнять разовые императивные команды» (типа удалённого kubectl через Kafka).

## Вариант B — «Оператор на controller-runtime» (декларативный)

На базе `sigs.k8s.io/controller-runtime`. Kafka-команды трактуются как **желаемое состояние**; informers/watchers + reconcile-петли приводят кластер к нему и постоянно поддерживают.

Два подвида:

- **B1:** команда из Kafka напрямую драйвит реконсайлер (Kafka — источник интентов).
- **B2:** команда из Kafka материализуется в **собственный CRD** (напр. `ClusterCommand`/`DesiredState`), а контроллер реконсайлит уже CRD. Получаем аудит, историю, статусы «из коробки» в etcd.

- ➕ Informers/watchers здесь «родные», leader election, кэши, rate-limiting — встроены.
- ➕ Самовосстановление состояния, ретраи, statuses.
- ➖ Сложнее, больше boilerplate, выше порог входа.
- ➖ Для чисто императивных команд («перезапусти под», «удали ресурс») — избыточно.

**Когда брать:** если нужно не «выстрелил и забыл», а **поддержание состояния** и реакция на изменения в кластере.

## Вариант C — Гибрид (рекомендуемый целевой)

Слой потребления Kafka отделён от слоя исполнения чётким интерфейсом `CommandHandler`:

- Старт делаем по **Варианту A** (быстрый результат, императивные команды + informers для кэша/валидации);
- Архитектуру сразу строим так, чтобы часть команд можно было перевести на reconcile-петли (Вариант B) без переписывания — общий dynamic-client слой, общий informer-факторинг, плагинная регистрация хендлеров по `command.type`.

Грубая структура пакетов:

```
cmd/agent/                 // main, wiring, leader election
internal/kafka/            // consumer group, DLQ, offset commit
internal/command/          // конверт, валидация, роутер по type
internal/handlers/         // обработчики: deployment, istio vs, ...
internal/k8s/              // dynamic client, RESTMapper, informers
internal/istio/            // обёртки над Istio CRD
internal/result/           // publisher статусов в Kafka
deploy/                    // манифесты: Deployment, RBAC, SA
```

## Вопросы для обсуждения (от ответов зависит выбор A/B/C)

1. **Характер команд:** произвольный «kubectl-as-a-service» или фиксированный allow-list операций? (Сильно влияет на безопасность и валидацию.)
2. **Зачем informers/watchers** в вашем сценарии: только кэш/валидация (→ A) или реакция на изменения и поддержание состояния (→ B)?
3. **Нужен ли синхронный результат** обратно в Kafka (топик-ответ) или достаточно метрик/логов/Events?
4. **Гарантии порядка/идемпотентности:** важен ли строгий порядок команд по одному ресурсу? Возможны ли дубли сообщений (at-least-once)?
5. **Один кластер или мульти-кластер** (агент управляет только своим кластером, где живёт, или ещё внешними)?
6. **Безопасность источника команд:** как авторизуем, что команда легитимна (подпись сообщения, ACL на топик, mapping issuer→разрешённые namespaces)?
7. **Какие Istio-ресурсы** реально нужны (VirtualService, DestinationRule, Gateway, AuthorizationPolicy…) — определит, типизированный клиент или dynamic.
8. **Масштаб/нагрузка:** ориентировочный rate команд и число партиций топика?
9. **Kafka-инфра:** есть ли Schema Registry, какой формат сообщений предпочтителен (JSON/Avro/Protobuf)?
10. **dry-run/подтверждения** для опасных операций (delete/scale-to-zero) — нужны?
