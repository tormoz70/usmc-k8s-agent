Как работает @uamc-agent/

    @uamc-agent/ — это отдельный Spring Boot микросервис (не часть uamc-core), который разворачивается внутри кластера Kubernetes как sidecar-компонент. Он взаимодействует с uamc-core через Kafka, а с самим кластером — через
    Kubernetes API.

    Архитектура

    Агент собирается как единый uber-JAR (uamc-agent.jar), но внутренне разделён на профили Spring (вместо обычных бинов):

      1 uamc-agent/
      2 ├── uamc-agent/                      # главный модуль (AppConfig + профили)
      3 ├── uamc-agent-commons/              # общие утилиты, исключения, конфиги
      4 ├── uamc-agent-kubeapi/              # клиент Kubernetes API
      5 ├── uamc-agent-eventswatcher/        # наблюдатель за событиями кластера
      6 ├── uamc-agent-metricswatcher/       # сбор метрик
      7 ├── uamc-agent-loglevel/             # управление уровнями логирования
      8 ├── uamc-agent-ailogscollector/      # сбор логов для AI агента
      9 ├── uamc-agent-ottlogswatcher/       # сбор логов OTT sidecar
     10 ├── uamc-agent-ottlogstruewatcher/   # watcher логов OTT-Sidecar
     11 └── uamc-agent-resourcewatcher/      # watcher ресурсов

    Ключевая особенность: все бины (@Controller, @Component, @Service) должны определяться только в профильных AppConfig файлах (например, KubeApiAppConfig, AiLogsCollectorAppConfig). Это проверяется task'ом validateSources
    при сборке. Аннотации в обычных классах модулей запрещены.

    Профили и режимы работы

    Агент запускается с одним или несколькими профилями, каждый из которых подключает соответствующий модуль:


    ┌──────────┬────────────────────────────┬──────────────────────────────────────┐
    │ Профиль  │ Модуль                     │ Назначение                           │
    ├──────────┼────────────────────────────┼──────────────────────────────────────┤
    │ KUBEAPI  │ uamc-agent-kubeapi         │ proxy для доступа к API k8s          │
    │ EVENTSW  │ uamc-agent-eventswatcher   │ сбор событий кластера                │
    │ LOGLEVL  │ uamc-agent-loglevel        │ управление уровнями логов для Tengri │
    │ AILOGSC  │ uamc-agent-ailogscollector │ сбор логов для AI агента             │
    │ OTTLOGSW │ uamc-agent-ottlogswatcher  │ watcher логов OTT-Sidecar            │
    │ METRICSW │ uamc-agent-metricswatcher  │ сбор метрик                          │
    └──────────┴────────────────────────────┴──────────────────────────────────────┘


    Конфигурация из application.yml:

     1 spring.profiles.active: KUBEAPI,EVENTSW,LOGLEVL,K8S,METRICSW,AILOGSC

    Взаимодействие с uamc-core

    Агент работает по асинхронной request-response модели через Kafka:

     1. Запросы от ядра приходят в топик in-requests:

     1    uamc-core.ssl.request.{cluster-id}-{uamc-agent}
     2. Ответы агенту приходят в топик:

     1    uamc-agent.ssl.response.{cluster-id}-{uamc-agent}
     3. Запросы от агента к ядру отправляются в топик:

     1    uamc-agent.ssl.request
     4. Адресат сообщений — "uamc-core", отправитель — cluster-name агента.

    API контракты (REST)

    Агенты не вызывают друг друга напрямую через REST — всё идёт через Kafka. Но модуль uamc-agent-kubeapi сам предоставляет REST-endpoint как proxy к Kubernetes API для UI (uamc-ui). Это позволяет UI работать с k8s без
    прямого доступа к API кластера.

    Также модули предоставляют REST API для управления:
     - OttLogsStartWatchingController / OttLogsStopWatchingController — старт/стоп сбора логов
     - LLController — запросы на изменение уровня логирования
     - UpdateLLCacheController — приём обновлений от ядра
     - AiLogsCollectorCollectLogsController / AiLogsCollectorGetPodsController — сбор логов AI

    Kafka контракты

    Контракт описан в CoreClient.java через protobuf-сообщения:

     1 ProtoHeaders:
     2   - messageId, correlationId: UUID
     3   - topic, topicForResponse: String
     4   - direction: REQUEST | RESPONSE
     5   - addressee: "uamc-core"
     6   - sender: cluster-name
     7   - messageType: имя класса protobuf-сообщения
     8   - requestType: тип запроса (enum RequestType)
     9   - timestamp: ISO LocalDateTime

    Дополнительные топики из конфига:

     1 out-request-topic: uamc-agent.ssl.request
     2 out-request-topic-to-events-consumer: uamc-events-watcher.ssl.request
     3 out-request-topic-to-metrics-consumer: uamc-metrics-watcher.ssl.request

    Ключевые параметры Kafka:
     - auto.offset.reset: latest — только новые сообщения
     - enable.auto.commit: true с auto.commit.interval.ms: 3000
     - max.poll.records: 10
     - pause-after-each-poll-ms: 1000 — пауза между poll
     - in-response-topic-timeout-ms: 10000 — таймаут ожидания ответа
     - in-heartbeat-timeout-ms: 2000

    Внутренние паттерны

     1. Cache-Aside — кэши с TTL для конфигов, кластеров, событий, метрик
     2. Key-Based Synchronization (StringKeySynchronizer) — потокобезопасная обработка запросов по ключу {cluster}/{namespace}/{object}
     3. Двойная проверка в LLService: перед запросом в ядро проверяется актуальность через LLCache.updateNewRequest()
     4. Reactive batching в OttLogSendBuffer — реактивная отправка пачек логов
     5. Self-registration — агент при старте регистрирует себя в ядре (с настраиваемыми задержками)

    Дополнительные зависимости

    Агент использует S3cloud (s3cloud.sbrf.ru, bucket uamc-transfer) для передачи артефактов (логи, дампы). Доступ через переменные окружения:

     1 S3CLOUD_ACCESS_KEY_ID
     2 S3CLOUD_SECRET_ACCESS_KEY

    Также используется gRPC (порт grpc.server.port в конфиге) — для каких-то внутренних вызовов (например, в healthcheck-сценариях).

    Контракты, которым должен соответствовать @uamc-agent/

    Kafka контракты:
     - Поддержка топиков uamc-agent.ssl.request (исходящие), uamc-core.ssl.request.* (входящие), uamc-agent.ssl.response.* (ответы)
     - Формат сообщений: protobuf с заголовками ProtoHeaders (messageId, correlationId, requestType, sender, addressee="uamc-core")
     - Параметры consumer/producer в соответствии с конфигом выше

    API контракты:
     - REST proxy к Kubernetes API (модуль uamc-agent-kubeapi)
     - REST контроллеры для операций модулей (старт/стоп watchers, изменение уровней логов)
     - gRPC сервер для служебных вызовов

    Кросс-кластерная маршрутизация:
     - Каждый агент уникален по {cluster-id}-{uamc-agent} в имени топика
     - Поддержка multi-cluster через cluster-name в заголовках

    Helm/Kubernetes:
     - Деплой через Helm chart из uamc-agent/helm-k8s
     - Генерация Helm/Dockerfile через Gradle tasks (makeDockerfile, filterCopyfile)
     - Ресурсы: helm-k8s/, openshift-template/, efs-config/

### ASSISTANT
Ниже — практичный план миграции `@uamc-agent/` с Java/Spring Boot на Go. Я бы шёл не через «переписать всё разом», а через поэтапный перенос с сохранением всех внешних контрактов: Kafka, protobuf, REST, gRPC, Kubernetes API, Helm, S3.

Ключевая идея: **Go-агент должен стать тем же sidecar-компонентом с теми же контрактами, но без Spring-магии**. Профили Spring лучше заменить явной конфигурацией модулей, а аннотации — обычной композицией зависимостей.

# 1. Что важно зафиксировать до начала миграции

До написания Go-кода нужно зафиксировать внешние контракты, потому что именно они являются границей совместимости с `uamc-core`, `uamc-ui`, Kubernetes и другими агентами.

## 1.1. Kafka-контракты

Нужно явно описать:

### Входящие топики

Запросы от `uamc-core`:

```text
uamc-core.ssl.request.{cluster-id}-{uamc-agent}
```

### Исходящие топики

Ответы агента:

```text
uamc-agent.ssl.response.{cluster-id}-{uamc-agent}
```

Запросы от агента к ядру:

```text
uamc-agent.ssl.request
```

Дополнительные топики:

```text
uamc-events-watcher.ssl.request
uamc-metrics-watcher.ssl.request
```

### Параметры consumer/producer

Нужно сохранить или осознанно заменить:

```yaml
auto.offset.reset: latest
enable.auto.commit: true
auto.commit.interval.ms: 3000
max.poll.records: 10
pause-after-each-poll-ms: 1000
in-response-topic-timeout-ms: 10000
in-heartbeat-timeout-ms: 2000
```

В Go это не обязательно переносить 1-в-1, но поведение должно быть совместимым: offsets, таймауты, порядок обработки, паузы, retry, идемпотентность.

# 2. Целевая архитектура Go-агента

На Go не нужно воспроизводить Spring Boot один в один. Лучше сделать явно собираемое приложение с модулями.

## 2.1. Общая идея

В Java у тебя:

```text
Spring profiles -> модули -> бины -> автоконфигурация
```

В Go лучше сделать:

```text
config -> module registry -> explicit constructors -> app runner
```

То есть конфигурация определяет, какие модули включены:

```yaml
agent:
  modules:
    - kubeapi
    - eventswatcher
    - loglevel
    - metricswatcher
    - ailogscollector
    - ottlogswatcher
```

Каждый модуль явно регистрируется в приложении.

# 3. Соответствие Java/Spring и Go

| Java/Spring | Go-эквивалент |
|---|---|
| Spring Boot application | `main.go` + app runner |
| Spring profiles | config `modules.enabled` |
| `@Component`, `@Service` | explicit constructors |
| `@Configuration` | bootstrap/factory packages |
| Spring DI | manual DI, `google/wire`, `uber-go/fx` |
| `application.yml` | `koanf`, `viper`, `envconfig` |
| KafkaListener | consumer worker/goroutine |
| RestTemplate/WebClient | `net/http.Client` |
| Spring MVC controllers | `chi`, `echo`, `gin`, `net/http` |
| Spring Cache | `ristretto`, `go-cache`, custom TTL cache |
| `synchronized`, locks | `sync.Mutex`, `sync.RWMutex`, keyed locks |
| Reactor / reactive batching | channels, tickers, worker pools |
| Gradle modules | Go packages/modules |
| Gradle tasks | Makefile/Taskfile/goreleaser |
| uber-JAR | static Go binary |
| Spring Actuator | custom `/healthz`, `/readyz`, `/metrics`, pprof |

## 5.4. CoreClient

## 5.7. Key-Based Synchronization

В Java есть `StringKeySynchronizer` для ключей вида:

```text
{cluster}/{namespace}/{object}
```

В Go нужен аналог.

Варианты:

1. Custom keyed mutex.
2. `golang.org/x/sync/singleflight`.
3. `github.com/teambition/rrlock-go`.
4. Semaphore per key.

Пример custom keyed locker:

```go
type KeyedLocker struct {
    mu    sync.Mutex
    locks map[string]*sync.Mutex
}
```

Но лучше делать с reference counting, чтобы не текла память:

```go
type keyLock struct {
    mu       sync.Mutex
    refCount int
}
```

Поведение:

```text
Запросы с одним ключом обрабатываются последовательно.
Запросы с разными ключами обрабатываются параллельно.
```

## 5.8. Reactive batching replacement

В Java есть `OttLogSendBuffer` с реактивной отправкой пачек.

В Go это реализуется через:

```text

ticker
batch size
flush timeout
worker pool
context cancellation
```

Пример логики:

```text
logs -> channel -> batcher
batcher accumulates until:
  - batch size reached
  - flush interval reached
  - context cancelled
  - buffer limit reached
then sends batch
```

Нужно продумать:

- backpressure;
- max buffer size;
- drop policy;
- retry;
- ordering;
- duplicates;
- partial failure.

# 11. Concurrency и надёжность

Go даёт простую конкурентность, но нужно аккуратно заменить Java-паттерны.

---

## 11.1. Graceful shutdown

Нужно обработать:

```text
SIGTERM
SIGINT
preStop hook
context cancellation
```

Порядок:

```text
1. Получить сигнал.
2. Остановить прием новых HTTP/gRPC запросов.
3. Остановить Kafka consumers.
4. Дождаться обработки текущих сообщений.
5. Flush producers.
6. Закрыть connections.
7. Завершить процесс.
```

---

## 11.2. Goroutine leaks

Нужно:

- всегда передавать `context.Context`;
- всегда иметь способ остановить goroutine;
- использовать `sync.WaitGroup`;
- не запускать бесконечные goroutine без shutdown;
- проверять утечки в тестах через `goleak`.

---

## 11.3. Backpressure

Для Kafka и log batching:

```text
bounded channels
worker limits
drop policy
retry queue
circuit breaker
rate limiter
```

---

## 11.4. Idempotency

Так как Kafka может давать повторы, нужно обрабатывать:

```text
messageId
correlationId
requestType
```

Если операция не идемпотентна, нужен deduplication cache или external state.

## 13.1. Dockerfile

Пример multi-stage:

```dockerfile
FROM golang:1.24 AS build

WORKDIR /src

COPY go.mod go.sum ./
RUN go mod download

COPY . .

RUN CGO_ENABLED=0 GOOS=linux go build \
    -ldflags="-s -w" \
```

Если используется `confluent-kafka-go`, может понадобиться `CGO_ENABLED=1` и образ с `librdkafka`.

Тогда лучше:

# 14. Стратегия перехода

Я бы не заменял Java-агент на Go сразу везде.

---

## 14.1. Рекомендуемая схема

### Шаг 1. Freeze Java features

Заморозить функциональность Java-агента, кроме bugfix.

### Шаг 2. Build Go skeleton

Сделать пустой сервис с:

```text
config
logging
health
metrics
http
grpc
kafka
k8s client
```

### Шаг 3. Contract compatibility

Добиться, чтобы Go-сервис:

```text
понимал входящие protobuf-сообщения;
умел отправлять корректные ответы;
проходил contract tests.
```

### Шаг 4. Enable one module

Например:

```text
eventswatcher
```

Запустить в test cluster.

### Шаг 5. Shadow mode

Если возможно, запустить Go-агент в shadow mode:

```text
Java agent продолжает обрабатывать запросы.
Go agent только наблюдает и пишет метрики/логи сравнения.
```

### Шаг 6. Canary cluster

Выбрать один некритичный кластер:

```text
Java agent выключен.
Go agent включён.
```

### Шаг 7. Gradual rollout

По одному кластеру:

```text
cluster-1 -> Go
cluster-2 -> Go
cluster-3 -> Go
```

### Шаг 8. Rollback plan

Для каждого кластера должна быть возможность быстро вернуть Java:

```text
helm rollback
или смена image tag
```

### ASSISTANT
Принято. Диаграммы сильно уточняют картину, особенно по модулю:

```text
uamc-agent-ottlogstruewatcher
profile: OTTLOGSWTRUE
```

Это не просто «watcher логов», а полноценный streaming pipeline:

```text
Scheduler
  → получение конфигурации через Kafka
  → запуск NamespaceCollector'ов
  → discovery pod'ов и OTT-sidecar'ов
  → запуск SidecarWatcher'ов
  → чтение логов из Kubernetes
  → накопление строк в bucket'ы
  → очередь на парсинг
  → парсер XACML-логов
  → буферизация записей
  → группировка по sidecar'ам
  → отправка protobuf-сообщений в Kafka
```

Ниже — обновлённый план миграции с учётом этих UML-диаграмм.

## 5.5. OttLogTrueNamespaceCollector

Это один из самых сложных компонентов.

Он отвечает за:

```text
1. Запуск SidecarProcessor.
2. Первоначальный список pod'ов.
3. Фильтрацию pod'ов по sidecarMask.
4. Обнаружение OTT-sidecar'ов.
5. Запуск SidecarWatcher'ов.
6. Deduplication по sidecarKey.
7. Запуск Pod informer.
8. Обработку add/update/delete событий.
9. Ожидание завершения всех watchers.
10. Вызов onCompletion(namespace).
```

---

### 5.5.1. Структура

```go
type NamespaceCollector struct {
    logger           *slog.Logger
    namespaceConfig  NamespaceConfigDto
    podsService      PodsService
    watcherFactory   SidecarWatcherFactory
    kube             kubernetes.Interface
    queue            chan Bucket
    processor        *SidecarProcessor
    onCompletion     func(namespace string)

    runnedWatchers   map[string]*SidecarWatcher
    completedSidecars map[string]struct{}
    watchersWG       sync.WaitGroup

    stopCh           chan struct{}
    stopOnce         sync.Once
}
```

---

### 5.5.2. Lifecycle

```text
start(config, onCompletion)
  1. processor.start(namespaceConfig)
  2. list pods
  3. filter pods by sidecarMask
  4. for each pod:
       detect sidecar
       if not completed and not running:
           start watcher
           add to runnedWatchers
  5. start pod informer
  6. wait until all watchers complete or stop requested
  7. close informer
  8. onCompletion(namespace)
```

---

### 5.5.3. Important: informer handlers не должны блокироваться

В Java диаграмме:

```text
onAdd → waitReady → runWatch
```

В Go, если использовать `SharedInformer`, handler'ы нельзя блокировать надолго.

Поэтому:

```go
AddFunc: func(obj interface{}) {
    pod := obj.(*v1.Pod)
    go c.handlePodAdd(ctx, pod)
}
```

Внутри:

```text
waitUntilCondition(pod, Ready=True, timeout=180s)
detect sidecar
start watcher
```

Иначе один pod, который долго становится Ready, заблокирует informer.

### 5.8.3. Auto-stop по scanPeriod

## 5.9. Healthcheck

Из диаграммы:

```text
Every healthcheckPeriodSecs:
  build OttLogTrueBucket:
    config = ConfigDto
    received = now()
    lines = empty
    healthcheckRecord = true
  put bucket to queue
```

На Go:

```go
func (w *SidecarWatcher) runHealthcheck(ctx context.Context) {
    ticker := time.NewTicker(w.config.HealthcheckPeriod)
    defer ticker.Stop()

    for {
        select {
        case <-ctx.Done():
            return
        case <-ticker.C:
            bucket := Bucket{
                Config:      w.config,
                Received:    time.Now(),
                Lines:       []string{},
                Healthcheck: true,
            }

            select {
            case w.queue <- bucket:
            case <-ctx.Done():
                return
            }
        }
    }
}
```

Важно:

```text
healthcheck bucket должен проходить через processor и parser chain, как в Java.
Он должен отправляться в Kafka даже если все XACML-поля пустые.
```

## 5.10. Bucketizer

Из диаграммы:

```text
recordsBatchSizeByLogger = 2
```

Логика:

```text
Если строка совпадает с checkLoggerNameRegex:
  это начало новой лог-записи.
  Если уже был открытый buffer — закрыть его.
  Начать новый buffer.
  Добавить строку.

Если строка не совпадает:
  Если buffer уже открыт — добавить строку как продолжение.
  Если buffer не открыт — игнорировать строку.

Если buffer size == 2:
  закрыть buffer.
  отправить в queue.
```

На Go:

```go
type Bucketizer struct {
    batchSize int
    regex     *regexp.Regexp
    buffer    []string
    started   time.Time
    inBuffer  bool
}
```

Метод:

```go
func (b *Bucketizer) ProcessLine(line string) []Bucket
```

Возвращает:

```text
0 bucket'ов — строка добавлена или проигнорирована;
1 bucket — buffer закрыт.
```

Нужно сохранить Java-поведение:

```text
String.join(" ", lines)
```

То есть bucket хранит массив строк, а парсер потом соединяет их через пробел.

## 5.12. OttLogTrueSidecarProcessor

Из диаграммы:

```text

```

На Go:

```go
func (p *SidecarProcessor) Run(ctx context.Context) {

        select {
        case <-ctx.Done():
            return
        case bucket, ok := <-p.queue:
            if !ok {
                return
            }
            p.process(ctx, bucket)
        }
    }
}
```

Но для graceful shutdown нужно аккуратно закрыть queue только после остановки всех watchers.

## 5.14. Важное предупреждение по regex

Java `Pattern` и Go `regexp` отличаются.

Go использует RE2, который не поддерживает:

```text
lookahead
lookbehind
backreferences
```

Если в Java regex есть что-то вроде:

```text
(?<=...)
(?=...)
\1
```

то в Go стандартный `regexp` это не поддержит.

Варианты:

1. Переписать regex без lookaround.
2. Использовать `github.com/dlclark/regexp2`, если нужна PCRE-совместимость.
3. Использовать ручной парсинг строк.

Рекомендация:

```text
Сначала извлечь точные Java-regex.
Проверить, используют ли они lookaround.
Если нет — использовать стандартный Go regexp.
Если да — переписать или использовать regexp2.
```

## 5.15. OttLogTrueSendBuffer

Из диаграммы:

```text

```

```text

2. record добавляется в buffer.
3. Если size >= 30 — flush.
4. Каждые 100ms проверяется:
   если buffer не пуст и прошло > 30000ms — flush.
5. При flush:
   sender.send(batch)
```

---

### Go-реализация

```go
type SendBuffer struct {
    logger     *slog.Logger
    sender     Sender
    maxSize    int
    timeout    time.Duration
    checkEvery time.Duration

    input      chan Record
    stopCh     chan struct{}
    wg         sync.WaitGroup
}
```

Внутренний цикл:

```go
func (b *SendBuffer) Run(ctx context.Context) {
    ticker := time.NewTicker(b.checkEvery)
    defer ticker.Stop()

    var records []Record
    var lastReceived time.Time

    for {
        select {
        case <-ctx.Done():
            b.flush(records)
            return

        case rec := <-b.input:
            if len(records) == 0 {
                lastReceived = time.Now()
            }
            records = append(records, rec)

            if len(records) >= b.maxSize {
                b.flush(records)
                records = nil
            }

        case <-ticker.C:
            if len(records) > 0 && time.Since(lastReceived) >= b.timeout {
                b.flush(records)
                records = nil
            }
        }
    }
}
```

Но нужно уточнить Java-семантику timeout:

```text
timeout считается от первой записи в буфере?
или от последней?
или от последнего flush?
```

Из диаграммы похоже:

```text

```

Скорее всего от первого элемента в текущей пачке.


# 15. Моя обновлённая рекомендация

С учётом этих диаграмм я бы не начинал миграцию с `OttLogTrueWatcher`, если есть другие более простые модули.

Лучший порядок:

```text
1. Core infrastructure.
2. Kafka + protobuf + ProtoHeaders.
3. Kubernetes client.
4. eventswatcher / metricswatcher / resourcewatcher.
5. Только потом OttLogTrueWatcher.
```

Почему:

```text
OttLogTrueWatcher содержит почти все сложные паттерны:
- Kafka request-response;
- Kubernetes informers;
- Kubernetes log streaming;
- prototype-like objects;
- concurrent queues;
- regex parsing;
- batching;
- compression;
- healthchecks;
- callbacks;
- graceful shutdown.
```

Если сначала обкатать инфраструктуру на более простых модулях, `OttLogTrueWatcher` пойдёт быстрее и безопаснее.
